## Goals / Non-Goals

Goals: the nine points as the reviewer and the house conventions describe them, with no field renamed and no stored value rewritten; the admin behaviour proven by unit and component tests; 0.4.0 publishable by the existing release workflow.

Non-goals: visitor code (point 9: the reviewer chose the admin hint), pick-lists for the email row's field references, migrating 0.3.0 questions to the prefill lock, the starter's pin.

## Research

### Payload's slug field (payload@3.92.1 and @payloadcms/ui@3.92.1, read from unpkg on 11 Nov 2026)

Read: `https://unpkg.com/payload@3.92.1/dist/fields/baseFields/slug/index.js`, `.../slug/generateSlug.js`, `https://unpkg.com/payload@3.92.1/dist/utilities/slugify.js`, `https://unpkg.com/@payloadcms/ui@3.92.1/dist/fields/Slug/index.js` and `index.scss`. No `node_modules` in this job folder.

- `slugField()` returns a `row` of two fields: a hidden checkbox `generateSlug` (`defaultValue: true`, `admin.hidden: true`, a `beforeChange` hook) and the `slug` text field whose admin component is `@payloadcms/next/client#SlugField`. The lock state that persists is the checkbox; the hook regenerates the slug from `useAsSlug` while it is true (on create unless the editor typed a slug; on update when there is no autosave).
- The `SlugField` component keeps `isLocked` in local `useState(true)`, renders the input read-only while locked, and shows "Unlock"/"Lock" and, when unlocked, "Generate" buttons inside the input (`.slug-field-component__actions`, absolutely positioned). Its `onChange` is `setValue` with the raw text: **Payload's slug field does not format as you type**; formatting happens in the save hook (`slugify`: trim, spaces to `-`, strip non-word characters, lower-case) and on "Generate".
- Consequence for point 4: we copy the persisted-checkbox half of the pattern (a hidden `prefillFromKey`, like `generateSlug`) and a lock/unlock button in the input, but our component reads the lock from the checkbox, not from local state, so a locked question shows as locked after reload. Consequence for point 5: "like Payload's slug field" describes the target format, not Payload's timing; formatting on each keystroke is ours to build.

### Default values and the database (@payloadcms/drizzle@3.92.1, payload@3.92.1)

- `@payloadcms/drizzle/dist/schema/withDefault.js`: a field's **static** `defaultValue` becomes the column's database default; a **function** `defaultValue` adds none. So a new checkbox with `defaultValue: true` would make the generated migration fill every existing row with `true`, and a function default leaves existing rows `NULL`.
- `payload/dist/fields/hooks/beforeValidate/promise.js:182-243` with `getFallbackValue.js`: for an undefined incoming value Payload uses the stored row's value when there is one (`siblingDoc`), else the field's default (functions are called). So a new block row gets the default and an existing 0.3.0 row keeps its stored `NULL`, also on API updates that omit the field. Field `beforeValidate` runs before the collection's `beforeValidate` hook, so `validateFormBeforeSave` sees the resolved value. Pinned by tests (spec › "New question prefills by its key", "0.3.0 question with no parameter stays unprefilled").
- Whether Payload's admin applies a function `defaultValue` to a block row added in the form: not checked (it is documented for `buildFormState`); pinned by the component test "new question shows locked" through the `prefillFromKey !== false && value is not null` rule in design 4, and by the planner's browser check.

### Format as you type

- A controlled input that rewrites its value moves the caret to the end in React when the text changes length. The formatter only lower-cases, replaces runs of other characters with one `-` and drops a leading `-`; it keeps one trailing `-` so "project " can continue to "project-type". The component restores the caret by counting the characters before it that survive formatting. jsdom does not model caret movement reliably: the unit test pins the formatter and the caret arithmetic as pure functions; the caret feel is a planner browser check.
- `normalizeKey` (`src/shared/rules.ts:14-23`) stays the save-time and server guarantee: `formatKeyInput(x)` with trailing `-` removed equals `normalizeKey(x)` for every test string.

### Pick-lists from form state (@payloadcms/ui@3.92.1)

- `@payloadcms/ui` exports `useField`, `useFormFields(selector)`, `useAllFormFields`, `SelectInput`, `TextInput`, `FieldLabel` and `FieldDescription` from its client entry (`dist/exports/client/index.d.ts`); `useFormFields` uses `use-context-selector` (`dist/forms/Form/context.d.ts`), so a selector that returns a joined string re-renders the pick-list only when the key list changes, not on every keystroke elsewhere. We use `useFormFields` with such a selector, not `useAllFormFields` (which re-renders on every change).
- Form-state paths are flat: `sections.<s>.fields.<f>.fieldKey`, `sections.<s>.fields.<f>.blockType`, `sections.<s>.key`. The list is built from these paths, so unsaved keys appear at once.
- Behaviour of `SelectInput` with a value not in its options: not checked; the component adds such a value as its own option ("<key> (not in this form)") so nothing is hidden or lost.

### Checkbox alignment (@payloadcms/ui@3.92.1 `fields/Row/index.scss`, `fields/Checkbox/index.scss`)

- Row children are `flex-direction: column; justify-content: flex-start`, so each field starts at the top of the row. Text and select fields render a label above the input; the checkbox renders its label inline to the right, so the box sits a label's height above the inputs beside it, and a description under a neighbour adds height below, not above.
- Fix: one shared style constant `LEVEL_CHECKBOX_STYLE = { paddingTop: 'calc(var(--base) * 1.6)' }` (label line plus its padding) on the checkbox field's `admin.style`. Payload passes `admin.style` to the field wrapper (documented field admin option). The exact offset against the label height at every breakpoint is not checked here: the planner checks it on the starter QA site at 1366 and 390 (`row__fields` drops to block layout below `mid-break`, where the padding adds a little space above the checkbox, which is acceptable). A wrong offset is a constant tweak inside task 1.1, not a new plan.

### Clearing a radio answer

GOV.UK Design System, Radios: "If it's possible that none of the options apply, include 'None of the above' or 'I do not know'" and avoid a pre-selected option; native radios cannot be unset by the visitor. **Decided by the reviewer (11 Nov 2026): option A**, an admin hint telling editors to add "None of the above" or "Not sure"; no visitor code. The "Clear selection" link is not built.

## Decisions

1. **Level checkboxes (point 1).** New `src/collections/adminStyle.ts` exports `LEVEL_CHECKBOX_STYLE` (Research). Apply it to `required` (`blocks.ts:74-79`) and to both `enabled` checkboxes (`forms.ts:108`, `:176`). Widths, names and defaults unchanged.
2. **Rule labels (point 2).** Both `rows` arrays get `labels: { singular: 'Rule', plural: 'Rules' }` and `label: 'Rules'`. `name: 'rows'` and every `dbName` stay. `targetSectionKey` gets `label: 'Next section'`, rule `fieldKey` gets `label: 'Field'`.
3. **Field order (point 3).** Split `baseInputFields` into `headFields(defaultValue)` (key row, words), `prefillRow(defaultValue)` and `ruleGroupField()`. A built-in input block is `[...head, ...typeFields, ...prefillRow, rules]`; the radio block's type fields are its choice fields followed by the hint of decision 9. An app-defined type (`blocks.ts:313-315`) is `[...head minus own names, ...entry.block.fields, ...prefillRow minus own names, rules unless owned]`. `baseInputFields()` stays exported and returns the new order for apps that call it. Names unchanged: a test compares every data path of every built-in block (flattened, rows/collapsibles transparent) with `tests/fixtures/field-paths-0.3.0.json`, generated from `492852b` before any edit; the only new path is `prefillFromKey`.
4. **Prefill lock (point 4).**
    - Field: `prefillFromKey`, `type: 'checkbox'`, `admin.hidden: true`, `defaultValue: () => true` (a function, so no database default and existing rows stay `NULL`; Research), in the prefill row before `prefillParam`. `prefillParam` gets `admin.components.Field: 'payload-dynamic-forms/client#PrefillParamField'`, label and description unchanged in meaning: "Link parameter that prefills this answer. Locked: the key."
    - Meaning: locked when `prefillFromKey === true`. `false` or `null` (a 0.3.0 question) is unlocked.
    - Save (`validateFormBeforeSave`, after the key is normalised at `validateForm.ts:123-125`): locked → `prefillParam = fieldKey`; unlocked → `prefillParam` trimmed and kept, empty stays empty. File uploads (`initialAnswers` skips them, `rules.ts:335`) are left alone and the component hides the lock for them.
    - Admin (`PrefillParamField`): reads `prefillFromKey` and the sibling `fieldKey` with `useFormFields`; locked shows the formatted key read-only and follows it live; "Unlock" sets `prefillFromKey` false and keeps the current text editable; "Lock" sets it true and copies the key. A 0.3.0 row (`null`) shows unlocked with its stored text (empty stays empty).
    - Read side unchanged: `initialAnswers` still reads `prefillParam`, so visitors see a difference only once a question is saved locked.
5. **Keys as you type (point 5).** `src/admin/keys.ts` (pure, no React): `formatKeyInput(raw)` and `caretAfterFormat(raw, caret)`. `KeyField` (`payload-dynamic-forms/client#KeyField`) wraps `TextInput` with `useField`, applies both on change. Used on question `fieldKey` and section `key`. Descriptions say "Lower-case letters, numbers and dashes. Used in rules, links and {{tokens}}." Save-time `normalizeKey` unchanged.
6. **Two choices (point 6).** `choiceFields(sources, { minOptions })`: radio and select pass 2, checkbox group passes none. Typed `options` gets `minRows: 2`. Save check in `validateFormBeforeSave` for radio and select only (Payload's own `minRows` check on a field hidden by `admin.condition` is not checked, so the hook is the guarantee): typed with fewer than 2 rows; `sourceItems` with exactly 1 item; `sourceItems` empty and fewer than 2 published items in the source collection (`req.payload.count` with `_status: published` where the collection has drafts, as the empty-pick read does in `src/server/forms.ts:113-140`). Message: "<label or key>: a radio (or select) needs at least 2 choices." with the path of the options or source field. The check runs on every save, like the other checks in this hook.
7. **Pick-lists (point 7).** `src/admin/formKeys.ts` (pure): `fieldKeyOptions(formState)` and `sectionKeyOptions(formState, ownSectionIndex)` from the flat paths (Research), keys normalised, duplicates once, form order. `RuleFieldKeyField` on the rule `fieldKey`: a `SelectInput` of input-field keys plus an "Attribute (optional)" text input shown when the chosen field takes its options from a collection; stored value `key` or `key.attribute` (the format `splitRuleKey` reads, `rules.ts:29-40`). `SectionTargetField` on `targetSectionKey`: section keys except its own section (a self-target is a loop). A stored value not in the list is shown as "<key> (not in this form)" and the save check (`validateForm.ts:142-173`) still refuses it. Both fields stay `type: 'text'`.
8. **Step by step default (point 8).** `presentationMode` `defaultValue: 'steps'` (static, so the column default changes too; Research). Option order puts "Step by step" first. `src/server/forms.ts:189` keeps reading a null as single page, so no saved form changes mode. Saved values are never rewritten.
9. **Optional radio hint (point 9, decided by the reviewer: option A).** A `ui` field `noAnswerHint` in the radio block after its choice fields, `admin.condition: (_d, sibling) => !sibling?.required`, `admin.components.Field: 'payload-dynamic-forms/client#NoAnswerHint'`, which renders a `FieldDescription`: "Optional question: once visitors pick an answer they can't clear it. If no answer is valid, add a choice such as “None of the above” or “Not sure”." A `ui` field stores nothing.
10. **Client entry.** `src/exports/client.ts` starts with `'use client'` and re-exports `KeyField`, `PrefillParamField`, `RuleFieldKeyField`, `SectionTargetField`, `NoAnswerHint` from `src/admin/*.tsx`. `package.json` `exports['./client']` (types, import, default under `./dist/exports/client.*`); `tsconfig.json` `paths` maps `payload-dynamic-forms/client` to `./src/exports/client.ts` (the dev app resolves import-map paths through it); `tsconfig.build.json` includes `./src/**/*.tsx`. The swc build keeps the directive (check: `head -1 dist/exports/client.js`). Peers: `@payloadcms/ui ^3.92.1`, `react ^19.2.1` (inside `@payloadcms/ui@3.92.1`'s own React range). Nothing in `src/index.ts`, `src/collections/*` or `src/shared/*` imports React or `@payloadcms/ui` at runtime; the fields name the components by path string only.
11. **Dev app import map.** Regenerate `dev/app/(payload)/admin/importMap.js` with `yarn generate:importmap`; the boot test proves the dev app loads.
12. **Tests for admin behaviour.** Pure logic in `tests/admin-logic.test.ts` (node). Components in `tests/admin/*.test.tsx` with `// @vitest-environment jsdom`, `@testing-library/react`, and `vi.mock('@payloadcms/ui', ...)` giving a small in-memory form state (`useField`, `useFormFields`, `SelectInput`, `TextInput`, `FieldLabel`, `FieldDescription`) so no Payload provider tree is needed. `vitest.config.js` includes `tests/**/*.test.tsx`. New devDependencies `jsdom` and `@testing-library/react` (versions current in the sandbox at build time, pinned exactly). They test what the components do with form state; the look in the real admin is the planner's browser check.
13. **Packed check.** `scripts/check-packed.mjs` also refuses a missing `./client` target, installs `@payloadcms/ui`, `react` and `@types/react` at the devDependency versions into the scratch app, resolves `payload-dynamic-forms/client` with `import.meta.resolve` (not imported at runtime: `@payloadcms/ui` imports `.scss`, which plain Node can't load) and typechecks an import of each of its five names; checks the built file starts with `'use client'`. The `ok` line becomes `ok <n> files, 3 entries resolve, types resolve (<dir>)`.
14. **Version 0.4.0** in `package.json`; README edits: Migrations 0.4.0 paragraph (the section below, shortened), Changelog 0.4.0 first, Install says to run `payload generate:importmap` after installing or upgrading, Field types describes the lock, pick-lists, two-choice minimum and step-by-step default, Compatibility unchanged (0.3.0 or later).

## Migration impact for sites

The starter's pin plan relies on this section.

- **Schema migration: yes, one, generated by each site** (`payload migrate:create` then `payload migrate`, as for 0.3.0). It adds a nullable boolean column `prefill_from_key` to every input block table of the forms collection (built-in and app-defined types) and to the matching versions tables, with no default, so existing rows are `NULL`. It changes the database default of the forms table's `presentation_mode` column from `singlePage` to `steps` (Postgres: `ALTER COLUMN ... SET DEFAULT`; SQLite: drizzle may rebuild the table and copy its rows, not checked). No column is renamed or dropped and no data is moved. `noAnswerHint` is a `ui` field and adds nothing. The exact generated SQL is not checked here; the starter plan generates it and reads it before applying.
- **Import map: yes.** Run `payload generate:importmap` after upgrading; without it the forms admin shows missing-component errors for the key, prefill and rule fields.
- **0.3.0 forms after upgrading:** every question keeps its saved prefill parameter: an empty one still prefills nothing, a typed one keeps working. These questions show as unlocked; an editor clicks Lock to make one follow its key. Saved forms keep their presentation mode; only new forms start step by step. Labels, order and the pick-lists change only the admin screen. A radio or select with fewer than two choices keeps rendering and accepting answers, but the next save of that form is refused until a choice is added.
- **New questions** (admin or API) start locked, so they are prefillable as `?<key>=`. Seed scripts that create questions without `prefillFromKey` get the same, unless they pass `prefillFromKey: false`.

## Risks / Trade-offs

- **First admin components in the package.** Sites that skip `generate:importmap` see broken fields; README Install and Migrations say it, and the starter plan runs it. Mitigated by the packed check resolving and typechecking the client entry.
- **0.3.0 questions stay unlocked.** The reviewer wanted every question prefillable by key; doing that for saved forms would change live visitor behaviour (links with `?name=` would start prefilling) and rewrite stored data. New questions get it; editors opt old ones in.
- **Refusing one-choice radios on save** could block an editor mid-edit. Forms have no autosave, so only an explicit save meets it, with a message naming the question.
- **Caret position** while formatting: pinned as arithmetic, felt in the browser by the planner.
- **Parallel with job-055:** the security update (`framework-update-2026-11`, branch `update/2026-11-security`) changes `package.json` and `yarn.lock`. The 0.4.0 build may run in parallel; after job-055 merges, this branch is rebased onto `main` (expected conflict: `package.json`/`yarn.lock` only: keep both sides' changes, version 0.4.0, then regenerate the lock) and the planner's final review rerun runs on the rebased head. If job-055 moves Payload past 3.92.1, the planner re-reads the Research above for that version during the rerun.
