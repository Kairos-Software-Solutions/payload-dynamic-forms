## Goals / Non-Goals

Goals: the six decisions in `input/feedback.md`, exactly; every 0.4.0 form behaves as before after the upgrade (date questions stay Date mode with values as sent; carried defaults read the same); no column type, default or not-null change on any existing column; the admin behaviour proven by unit and component tests; 0.5.0 publishable by the existing release workflow.

Non-goals: the jump engine (unchanged by decision), visitor rendering (the starter pin plan), Payload's own form-state replacement after a save (decision 15), dropping the old localized default columns.

## Research

Source note: `input/forms-plugin-0-5-standards.md` (checked 12 Nov 2026) for the standards per point: Payload field types and its official form builder, Form.io, Gravity Forms, Jotform, Google Forms, Qualtrics skip vs display logic, HTML input value formats (WHATWG), TC39 Temporal, Payload issues #9775 and #12056. Everything below was read in the published 3.92.1 tarballs, unpacked read-only at `cache/scratch/pkg-src/{payload,ui,plugin-form-builder,drizzle}/package` (paths below are under each package's `dist/`).

### Defaults per type, and the database

- Payload's official form builder 3.92.1 (`collections/Forms/fields.js`): `defaultValue` is `type: 'number'` for number (`:351`), `checkbox` (`:498`), `date` (`:549`); select and radio keep localized text (`:63`, `:153`), the weak spot the reviewer hit. Its submissions collection sets `update: () => false` on the whole collection (`collections/FormSubmissions/index.js:95`).
- Column types (`@payloadcms/drizzle@3.92.1`): the column name comes from the field name, not `dbName` (`schema/traverseFields.js:40`); `email`, `textarea`, `code` and `text` are `varchar` (`:464-471`, `:769-787`), `date` is `timestamp` mode string (`:473-480`), `select` an enum (`:575-613`), `number` `numeric` (`:543-561`), `checkbox` `boolean` (`:455-461`). On SQLite, `varchar`, enum and `timestamp` all become `text`, `numeric` stays numeric and `boolean` is `integer` (`sqlite/schema/buildDrizzleTable.js:13-76`). So a text, email, select or date field is a `text` column, and a number field is not.
- `schema/withDefault.js:1-8`: a static `defaultValue` becomes the column default; a function adds none (house rule: new fields on existing data take a function default, and old rows read `NULL`).
- Localized fields live in the block's `_locales` table; making a field non-localized moves its column to the block table. For an app **with** localization, `defaultValue` of email, number, date, select and radio becomes a new column in the block table (ADD COLUMN) and the old `_locales.default_value` column is no longer read. For an app **without** localization, those columns already sit in the block table as `text`; email, select and date stay `text`, and a `number` field would change `text` → `numeric`, which drizzle-kit turns into a table rebuild (npm-package-release reference § 4). Consequence: decision 2.
- Payload's own date field stores a UTC instant, and its admin picker moves a day-only choice to 12:00 UTC of the picked day (`@payloadcms/ui` `elements/DatePicker/DatePicker.js:63-68`, `newDate.setHours(12 - tzOffset, 0)`). A form default is a wall-time value the visitor's browser should show as typed, so it is stored as the HTML text instead (decision 4). The picker itself (`DatePicker`, exported from `@payloadcms/ui` `exports/client/index.d.ts:36`) takes `pickerAppearance` `default | dayAndTime | dayOnly | monthOnly | timeOnly`, `displayFormat`, `timeFormat` and `timeIntervals` (`DatePicker.js:15-37`). Its own defaults don't suit a form default (`:34-56`): `dayOnly` shows `MMM dd` (no year), `dayAndTime` `MMM d, yyy h:mm a`, `timeOnly` `h:mm a`, times are 12-hour in 30-minute steps. For `dayOnly`, `default` and `monthOnly` it moves every pick to 12:00 UTC of the picked day (`:63-68`, `setHours(12 - tzOffset)`), which is the next local day at UTC+12 and beyond (Pacific/Auckland: pick 1 Dec, local getters read 2 Dec); `dayAndTime` and `timeOnly` picks stay as picked, in local time.
- `DateField` config (`payload` `fields/config/types.d.ts:539-553`): `admin.date` (`ConditionalDateProps`, where `pickerAppearance` lives) and `timezone?: true | config`, which adds a sibling select holding an IANA zone (`:505-538`). We take the mode names from it; the zone comes from the visitor's browser, not an editor's pick.

### Date and time values

- HTML (WHATWG): `date` = `YYYY-MM-DD`, `time` = `HH:MM` (`HH:MM:SS` with a seconds step), `datetime-local` = `YYYY-MM-DDTHH:MM` with no zone; the page can't set the display format of native inputs. TC39 Temporal names the kinds: PlainDate, PlainTime, PlainDateTime, ZonedDateTime/Instant; its `'compatible'` disambiguation moves a time in a spring-forward gap forward and takes the earlier of two fall-back times. Temporal is not used at runtime (not in every Workers/browser runtime); the conversion uses `Intl.DateTimeFormat` with `timeZone` (decision 10).
- Converting a calendar date to UTC can move it a day (a 9 pm entry in UTC-4); so only Date and time answers can opt into UTC (reviewer's follow-up, `input/feedback.md` decision 2).

### Field access (point 3)

- `payload` `fields/config/types.d.ts:86-110` (`FieldAccess`), `:305` (`access?: { create, read, update }`).
- `fields/hooks/beforeValidate/promise.js:218-245`: on update without `overrideAccess`, a field whose `access.update` returns false has its incoming value deleted and the stored value put back (`isDocumentValueAllowed` for update). The REST answer is still 200; the value just doesn't change.
- Order of an update (`collections/operations/utilities/update.js:20-23`, `:100-198`): field `beforeValidate` (access applied here) → collection `beforeValidate` → collection `beforeChange` → field `beforeChange` (no access check). The plugin's resend tick (`src/hooks/resendTick.ts:13-47`, the log set at `:44-46`) is a collection `beforeChange` hook that sets `data.deliveryLog` after field access ran, so an admin's tick still writes the log; every other system write (`src/endpoints/submit.ts:170-186`, `:228-233`, `src/endpoints/resend.ts:29-34`, `resendTick.ts:31-37`) uses the Local API with `overrideAccess: true`. Pinned by tests (spec › "System writes still update the record").
- Admin: a named field without update permission renders read-only (`@payloadcms/ui` `forms/RenderFields/index.js:49-68`).

### Rows and row labels (point 5)

- `@payloadcms/ui` `forms/fieldSchemasToFormState/isRowCollapsed.js:1-17`: a row's state comes from the previous form state, else the saved preferences, else `field.admin.initCollapsed`.
- **Planner's repro (12 Nov 2026).** (a) Plugin dev app, Payload 3.92.1: on a saved form, rows stay open through typing, ticking, adding an option, Save draft and a reload. On a new form, an opened section comes back closed after the first save: the create view has no preferences, so Payload falls back to the plugin's `initCollapsed: true`. (b) Starter test site: rows toggled while a save is in flight are undone on screen when the save returns (the form state sent with the save replaces the toggles), while the preference did save (a reload shows them toggled). (b) is `@payloadcms/ui`'s form `replaceState` after a save: Payload core, not the plugin. (a) is the plugin's own and shows in the plugin's dev app, not on the starter, which already opens sections and questions; on the starter only (b) remains.
- Array rows: `admin.components.RowLabel` (`payload` `fields/config/types.d.ts:1001-1010`), rendered per row with the row label server props (`@payloadcms/ui` `forms/fieldSchemasToFormState/renderField.js:95-110`). Block rows ignore the array's RowLabel: a block row gets a custom label only from its own block's `admin.components.Label` (`types.d.ts:1134-1146`; `renderField.js:113-141`), which replaces the whole header, number and type pill included (`fields/Blocks/BlockRow.js:139-160`).
- A client label reads its row through `useRowLabel()` → `{ data, path, rowNumber }` (`forms/RowLabel/Context/index.js`; exported from `exports/client/index.d.ts:192-193`). Server props (`blockType`, `rowLabel`) reach server components only; a `{ path, clientProps }` component config passes its `clientProps` to a client component (`elements/RenderServerComponent/index.js:40-50`), which is how a block label learns its type's name.
- The starter's labels (site-starter `origin/qa`, `src/plugins/forms/RowLabel.tsx`): `formRowText` (first non-empty of title, label, key, fieldKey, targetSectionKey, value; 72 characters; else "Row N"), `questionRowText` (label, heading, body, key) and the components `RowLabel` and `QuestionLabel` over `useRowLabel`. Ported, not redesigned (decision 16).

### Jumps (point 4)

- Reproduced in the research note: section 1 jumps to section 3 when `kind = a`, section 2 shows when `kind = a`; the path is s1, s3 for both answers. Qualtrics: skip logic sends respondents past everything in between; display logic decides only at arrival. Google Forms and Microsoft Forms "go to section" do the same. So the engine is standard; only the editor lacked a warning.

### Send another (point 6)

- Google Forms: "Show link to submit another response" (on by default). Payload's official builder: message or redirect. Gravity Forms: text, page or redirect. Cloudflare Turnstile tokens are single use (`src/security/turnstile.ts` sends each token once to siteverify).

## Decisions

1. **Default field per question type (point 1).**

   | Block | `defaultValue` in 0.5.0 | Admin input |
   |---|---|---|
   | text, textarea, app-defined types | unchanged: localized `text` | text |
   | email | `type: 'email'`, not localized | Payload's email input |
   | number | `type: 'text'`, not localized (decision 2) | `NumberDefaultField`: number input, Min/Max from the siblings |
   | date | `type: 'text'`, not localized | `DateValueField` (decision 4) |
   | select, radio | `type: 'text'`, not localized | `DefaultChoiceField` single (decision 3) |
   | checkbox group | unchanged column (`text`, not localized, comma-joined values) | `DefaultChoiceField` multi |
   | checkbox, file upload | unchanged | unchanged |

   Field name stays `defaultValue` everywhere, so the public form and renderers read the same key. Option `value`, `min`/`max`, `minDate`/`maxDate` are already not localized and stay so. Option `label` stays localized.
2. **Every default stays a text column.** Number defaults are stored as text so that no adapter sees a column type change (an app without localization would otherwise turn its existing `text` column into `numeric`, a rebuild on SQLite and a cascade delete on D1; Research › Defaults). The number input and the save check guarantee a finite number; `getPublicForm` and `defaultAnswer` give number questions a JavaScript number.
3. **Choice defaults are pick-lists (same pattern as 0.4.0's `SectionTargetField`).** `DefaultChoiceField` reads the question's typed options from the form state (`<question path>.options.<i>.value` and `.label`, unsaved edits included) and lists "label = value"; stores the value. Multi mode (checkbox group) lists the same with several picks and stores the values joined by `,` (the 0.4.0 format `toStringList` reads). A stored value not in the options stays listed as "<value> (not in the options)" and the save check names it. For choices from a collection, the field gets `clientProps.sources` (`{ [key]: { collection, labelField, valueField } }`, from the plugin's `optionSources`) and fetches the items through the REST API with the editor's session (`GET <serverURL><api>/<collection>?where[id][in]=…&depth=0&draft=true`, or the first 100 in the default sort when the pick is empty), listing them by label = value. No new endpoint.
4. **Date default and limits are pickers (`DateValueField`).** Wraps `@payloadcms/ui`'s `DatePicker` with `pickerAppearance` from the sibling `mode` (null → `dayOnly`) and these props per mode, so an editor always sees the year and a 24-hour clock: Date `displayFormat: 'yyyy-MM-dd'`; Date and time `displayFormat: 'yyyy-MM-dd HH:mm'`, `timeFormat: 'HH:mm'`, `timeIntervals: 15`; Time `displayFormat: 'HH:mm'`, `timeFormat: 'HH:mm'`, `timeIntervals: 15` (any minute can still be typed). Conversion to wall-time text (`YYYY-MM-DD`, `HH:MM`, `YYYY-MM-DDTHH:MM`) and back: Date mode reads a pick with the UTC getters (the picker hands it over as 12:00 UTC of the picked day, Research › Defaults, so this holds from UTC-12 to UTC+14) and gives the picker the local `Date` at 12:00 of the stored day (`new Date(y, m - 1, d, 12)`); Date and time and Time use the local getters and the local constructor (the picker leaves those as picked). Plus a "Today" choice (Date mode) or "Now" (Date and time, Time) that stores the token `today` (exported as `TODAY`). Pure conversion in `src/admin/dateText.ts`. Used on the date block's `defaultValue`, `minDate` and `maxDate` (labels "Earliest" and "Latest", names unchanged). For Time questions the limits are times and "Now" is not offered on limits (a time window has no "now").
5. **Save checks for defaults and limits.** `validateFormBeforeSave` becomes async and, for every input question, refuses (path `sections.<s>.fields.<f>.<name>`, message naming the question): an email default that is not one valid address; a number default that is not a finite number or lies outside Min/Max; a date default or limit that is not `today` or a valid value in the question's mode (`today` not allowed on Time limits), or Earliest after Latest when both are fixed; a select or radio default that is not one of its typed option values; a checkbox-group default with any value outside its options; a collection-choice default that is not the `valueField` of one of the picked items or, with an empty pick, of any item of that collection (read with `overrideAccess: true`, `draft: true`, so it never depends on another collection's publish state, as 0.4.0's two-choice check); a text or long-text default longer than Max length or, when not empty, shorter than Min length (the locale being saved). Empty defaults are always fine.
6. **Starting answers.** `defaultAnswer(field, ctx?)` and `initialAnswers(form, searchParams?, ctx?)` take an optional `{ now?: Date }`: `today` resolves in the runtime's local zone to the mode's format (`YYYY-MM-DD`; `YYYY-MM-DDTHH:MM` to the minute; `HH:MM`). Call them in the browser for "Today" defaults (README). A select or radio default outside the field's options (resolved options for collection choices) starts empty, and a checkbox-group default keeps only listed values, so a stale default can never make the visitor's first send invalid. Number defaults start as numbers. Link prefill still wins over the default, as in 0.4.0. `resolveDateLimit(field, 'min' | 'max', { now?, timeZone? })` gives a renderer the concrete value for an input's `min`/`max`.
7. **Date question settings (point 2).** New fields in the date block, in one row before the limits: `mode` (select, label "Asks for": Date `dayOnly`, Date and time `dayAndTime`, Time `timeOnly`), `valueFormat` (select, label "Stored as": "As the visitor's browser sends it" `local`, "UTC instant (ISO 8601)" `utc`; shown only for Date and time), `displayStyle` (select, label "In emails and messages": As stored `asStored`, Short, Medium, Long). Each has a function default (`() => 'dayOnly'`, `() => 'local'`, `() => 'asStored'`) and a short `dbName`, so no column default is added. The admin fills a default only when a value is `undefined`, not `null` (`@payloadcms/ui` `forms/fieldSchemasToFormState/calculateDefaultValues/promise.js:26`), so a 0.4.0 row's `NULL` would show a blank "Asks for": the sites' migration backfills the three on existing rows with a data `UPDATE` (Migration impact). Every reader still treats `NULL` as the default (Date, as sent, as stored), and `getPublicForm` fills the three on date questions, so renderers never see `null`.
8. **Answer checks per mode (`src/shared/answers.ts`).** Date: as 0.4.0 (`isValidDate`). Time: `HH:MM` or `HH:MM:SS`, 00:00-23:59. Date and time: `YYYY-MM-DDTHH:MM` or with `:SS`, a valid calendar date, no zone suffix. Limits compare in the same format (seconds ignored); `today` limits resolve through `CheckOptions.timeZone` (the visitor's zone, else the plugin's) and `CheckOptions.now`; a `today` Earliest on a Date and time question means 00:00 that day, a `today` Latest 23:59. Answers are kept exactly as sent (trimmed) unless decision 10 applies.
9. **The visitor's time zone.** Shared `TIME_ZONE_FIELD = '_tz'` (no field key can be `_tz`: keys are normalised to `[a-z0-9-]`) and `browserTimeZone()` (`Intl.DateTimeFormat().resolvedOptions().timeZone`). The renderer adds it to the submit body. The submit endpoint accepts it only when `Intl.DateTimeFormat('en-US', { timeZone })` accepts it, records it as the submission's `metadata.timeZone` (new text field) and uses it for decisions 8, 10 and 11; otherwise it uses the plugin option `timezone` and records nothing. New plugin option `metadata.timeZone` (boolean, default `true`, like `metadata.userAgent`; resolved next to `ip` and `userAgent` in `resolveOptions`): when `false`, a valid `_tz` is still used for that request (checks, conversion, the snapshot, WhatsApp text and the deliveries run in the same request) but not stored, so webhook bodies carry no zone and a later resend formats in the plugin's `timezone`. New plugin option `timezone` (IANA name, default `'UTC'`), checked at config time: an unknown zone throws `formsPlugin: timezone "<x>" is not a known IANA time zone.`
10. **UTC storage (opt-in).** Only for `mode: 'dayAndTime'` with `valueFormat: 'utc'`: after the checks pass, the submit endpoint replaces the answer with `toUtcInstant(local, zone)` (`Date.prototype.toISOString` form, e.g. `2026-11-12T19:30:00.000Z`), before the snapshot, the store and the deliveries. `toUtcInstant` (pure, `src/shared/dates.ts`) finds the offset with `Intl.DateTimeFormat(..., { timeZone, hourCycle: 'h23' }).formatToParts` and applies Temporal's `'compatible'` rule: a time in a spring-forward gap moves forward by the gap; an ambiguous fall-back time takes the earlier instant. Date-only and time-only answers are never converted, whatever `valueFormat` holds.
11. **Dates in messages.** `formatAnswerDate(value, field, { locale, timeZone })`: `asStored` (or null) returns the stored text; Short/Medium/Long use `Intl.DateTimeFormat(locale, …)`: Date → `dateStyle`, Time → `timeStyle: 'short'`, Date and time as sent → `dateStyle` + `timeStyle: 'short'`, all formatted with `timeZone: 'UTC'` from the wall-time parts so nothing shifts; a UTC-stored instant is formatted in the submission's recorded zone (else the plugin's) and followed by the zone name in brackets (`… (America/New_York)`), so a team reading it knows whose clock it is. A locale `Intl` rejects falls back to `en`. `answerToText` takes the context as an optional last argument and passes date questions through it; `buildSnapshot`, `buildMessageRows`, `buildTemplateValues` and `buildWhatsAppMessage` take the same optional context. Language: snapshot and WhatsApp text in the submission's language, visitor copy in the submission's language, team email in the default language (the 0.3.0 rule). Webhooks are unchanged in shape and carry the stored values; the full body adds `submission.timeZone` and the answers-only body adds `timeZone`, each only when a zone was recorded, so a body without a zone is byte-identical to 0.4.0. Resend (endpoint and sidebar tick, `src/server/resend.ts`) reads the zone from `metadata.timeZone`, so a resent message or webhook shows the same clock as the first send.
12. **Submission records are read-only (point 3).** `form`, `answers`, `snapshot`, `attachments`, `deliveryLog` and `metadata` get `access: { update: () => false }` (a shared `nobodyField`), kept alongside their `admin.readOnly`. `status` and `resendFailed` keep the collection's admin-only update. Delete stays admin-only. A submissions override (`submissionOverrides.fields`) can still replace them. System writes keep working (Research › Field access).
13. **Jumps (point 4).** `nextStepRules` gets `label: 'Jump to section when'`, `labels: { singular: 'Jump', plural: 'Jumps' }`, `admin.description: 'Skips every section in between, even ones whose show rules match.'`; its `targetSectionKey` label becomes "Jump to section". Names, condition (step-by-step forms only) and the engine are unchanged. A `ui` field `jumpSkipHint` right after `nextStepRules` in the section (`payload-dynamic-forms/client#JumpSkipHint`, condition step-by-step) lists, from the form state, each section that one of this section's jumps passes over (sections strictly between this one and the target, in form order) and that has at least one show rule with a field key; it renders nothing when there is none. Text: `Jump to “<target>” skips “<section>”, which has its own show rules. A jump skips every section in between; for an optional section, use its show rules instead of a jump.` (one line per skipped section). Pure logic `skippedSectionsWithShowRules(formState, ownIndex)` in `src/admin/formKeys.ts`.
14. **Every plugin list starts open (point 5, fixes repro (a); the planner's decision).** Payload's default, `initCollapsed: false`, set explicitly on every array and blocks field the plugin adds: `sections`, the questions blocks field, both rule `rows` arrays, `nextStepRules` (jumps), `delivery.emails`, `delivery.webhooks`, webhook `headers`, typed `options`, and the submission's read-only `deliveryLog` and `snapshot`. So no plugin list falls back to closed on a new form's first save (repro (a)); the row labels (decision 16) make rows the editor closes readable, and Payload remembers his toggles in his preferences. The starter already opens sections and questions, so on the starter this changes the settings lists only; the snap-back during a save (decision 15) stays.
15. **Known Payload behaviour (repro (b)), not changed.** Rows toggled while a save is in flight snap back on screen when the save returns, because `@payloadcms/ui` replaces the form state with the state it sent for the save; the preference itself saves, and a reload shows the toggles. That is Payload core; the plugin doesn't patch it. Evidence: Research › Rows, repro (b) on the starter's test site. It is what the reviewer saw on the starter, where sections and questions were already open. An upstream Payload issue with that repro is optional and needs the reviewer's yes first (a public post); not part of this change.
16. **Row labels, ported from the starter.** `src/admin/rowText.ts` (pure) ports `formRowText` and `questionRowText` from site-starter `origin/qa` `src/plugins/forms/RowLabel.tsx` (same fallbacks: first non-empty text, cut at 72 characters with `…`, else `Row N`) and adds the decided wording: `sectionRowText` → `key · title` (either alone when the other is empty), `questionRowText(row, n, typeLabel)` → `type · key · label` for inputs and `type · heading` / `type · body` for heading and help text (empty parts left out; the starter showed the name only, the reviewer's decision adds type and key), `ruleRowText` → `<field> <operator label in lower case> <value>` (value left out for "has a value" / "has no value"), `optionRowText` → `label = value`, `jumpRowText` → `Jump to <section>`. `src/admin/RowLabel.tsx` ports the starter's `RowLabel` (array rows, `useRowLabel`) with an optional `clientProps.kind` (`section`, `rule`, `option`, `jump`; none = the starter's generic text, used by emails, webhooks and headers) and `QuestionLabel` (block rows) with `clientProps.typeLabel` (the block's singular label, else its slug). Wiring: `RowLabel` on `sections` (kind section), both `rows` arrays (rule), typed `options` (option), `nextStepRules` (jump), `delivery.emails`, `delivery.webhooks` and webhook `headers` (generic); `QuestionLabel` as `admin.components.Label` on every built-in block and on app-defined types whose block sets no Label of its own. The starter pin plan can then drop its own `RowLabel.tsx` and the `adjust()` lines that set row labels and `initCollapsed`.
17. **Send another (point 6).** `sendAnother` checkbox right after `successType`, label "Show a 'Send another' button", condition `successType === 'message'`, function default `() => false`. New word `sendAnother` in `FormWords`/`DEFAULT_WORDS` ("Send another") and in the Form wording group, localized, with a function default `() => options.words.sendAnother` (the existing words keep their static defaults: changing those would change column defaults, a rebuild). `fillWords` fills a `NULL` at read; the admin doesn't (decision 7), and a site that makes the wording fields required (the starter does) would refuse the next publish of every 0.4.0 form, so the sites' migration backfills it (Migration impact). `PublicForm.sendAnother` is `true` only when the success type is message and the box is ticked. The renderer's part (reset with `initialAnswers(form, searchParams)`, back to step 1, fresh Turnstile token) is README text.
18. **Carry-over helper for sites' migrations.** Main entry export `carryOverDefault({ blockType, values, defaultLocale, options?, sourceValues?, min?, max?, mode? })` → `{ value: string | null, report: string[] }`. `values` are the old localized defaults by locale. It carries the default-locale value (trimmed) when it fits the 0.5.0 rules of decision 5 for that type (email valid; number finite inside Min/Max; date a valid `YYYY-MM-DD`; select/radio one of `options`; collection choices one of `sourceValues`, or carried with the report line "not checked against the collection" when none are given) and reports, never silently drops: a default-locale value that doesn't fit, and any other locale's value that differs from the carried one. Pure, Workers-safe, no database access; the site's migration reads the rows, calls it and writes the result (Migration impact). ## Migration impact for sites

The starter's pin plan builds its migration from this section. Table names below use the dev app's slug `custom-forms`; read the exact names from the generated SQL.

**Columns added (all nullable, no default):**

| Table (and its `_v` twin, e.g. `_custom_forms_v_blocks_date`) | Column |
|---|---|
| `custom_forms_blocks_email`, `_number`, `_date`, `_select`, `_radio` | `default_value` text (apps with localization only; without localization it exists already) |
| `custom_forms_blocks_date` | `mode`, `value_format`, `display_style` (text) |
| `custom_forms` / `_custom_forms_v` | `send_another` / `version_send_another` (integer) |
| `custom_forms_locales` / `_custom_forms_v_locales` | `wording_send_another` / `version_wording_send_another` (text) |
| `custom_form_submissions` (no versions) | `metadata_time_zone` (text) |

No existing column changes type, default or not-null. Text and long-text defaults, checkbox and checkbox-group defaults, limits and options stay where they are.

**Values that move.** For apps with localization, the 0.4.0 default of email, number, date, select and radio questions lives in `<block>_locales.default_value`, per locale. 0.5.0 reads the block table's new `default_value`. The migration copies the default-locale value into it, but only when it fits (decision 18); everything else goes into the migration's report, which `up()` prints and also writes to `forms-0.5.0-carry-over.txt` in the directory `payload migrate` runs from (keep that file: it is the lasting record). The old `_locales.default_value` column stays in place, but it is not a lasting copy: on every update Payload's database adapter deletes a document's block rows and re-inserts them and their `_locales` rows with the columns the current config knows (`@payloadcms/drizzle` `upsertRow/index.js:536-580`), so the old value is `NULL` after that form's first 0.5.0 save. Older version rows in the `_v` tables keep theirs until pruned.

**Backfill of the new settings.** The admin fills defaults only for `undefined`, not `NULL` (decision 7), so `up()` also writes the defaults into existing rows (data `UPDATE`s; no column default is added): `mode = 'dayOnly'`, `value_format = 'local'`, `display_style = 'asStored'` on every date block row; `send_another = 0` on every form; `wording_send_another` on every existing forms locales row, with the plugin's configured `words.sendAnother` ("Send another" unless the site set it). Sites with non-English locales should write each locale's own words there (one `UPDATE … WHERE _locale = '<code>'` per locale); otherwise those locales show the English words until edited. Each in the `_v` twin too.

**What 0.4.0 rows read as after the upgrade (with the copy and backfill):** date questions are Date, as sent, as stored: they accept and store `YYYY-MM-DD` as before, with the same limits, and the admin shows "Asks for: Date". Carried defaults read the same as before (select/radio values that matched an option, valid dates, emails, numbers). Defaults that didn't fit start empty for visitors and show empty in the admin; the report names each (form, section, question, old value, reason). Send another is off and its words read "Send another" (or the site's translation), so the next publish passes even where the starter makes every wording field required. Submissions keep everything; `metadata.timeZone` is `NULL`. Without the copy, every email, number, date, select and radio default would read empty: the copy is not optional for localized apps. Without the backfill, old forms show a blank "Asks for" and fail their next publish on the starter: it is not optional either. (Readers still treat a stray `NULL` as the default, so visitors are unaffected either way.)

**New save checks on old forms:** a checkbox-group default with a value outside its options, a text default longer than Max length, or a limit that is not a valid date now blocks the next save of that form until fixed (visitors unaffected). For apps **without** localization the same holds for select, radio, email, number and date defaults: they already sit in the block table's `default_value`, stay in that column with no carry-over (nothing to copy, no report), and any that doesn't fit decision 5 (a select default that isn't an option, an invalid email, a number outside Min/Max, a date that isn't `YYYY-MM-DD`) blocks the next save of its form until fixed, and starts empty for visitors (decision 6). The pin plan counts such forms on QA before its push (npm-package-release § 5 step 3).

**D1 and SQLite: hand-written migration.** Run `payload migrate:create`, keep its snapshot JSON (so later diffs start from 0.5.0), and replace its SQL with:

```sql
-- per table in the list above, and its _v twin:
ALTER TABLE custom_forms_blocks_date ADD COLUMN default_value text;
ALTER TABLE custom_forms_blocks_date ADD COLUMN mode text;
ALTER TABLE custom_forms_blocks_date ADD COLUMN value_format text;
ALTER TABLE custom_forms_blocks_date ADD COLUMN display_style text;
-- … email, number, select, radio: default_value; forms: send_another; locales: wording_send_another;
ALTER TABLE custom_form_submissions ADD COLUMN metadata_time_zone text;
```

then, in the same `up()`, the copy for each of the five block tables and each `_v` twin: `SELECT b.id, l._locale, l.default_value FROM custom_forms_blocks_select b JOIN custom_forms_blocks_select_locales l ON l._parent_id = b.id WHERE l.default_value IS NOT NULL AND trim(l.default_value) <> ''`, plus each question's option values (`SELECT _parent_id, value FROM custom_forms_blocks_select_options`), `min`/`max` for number, and `options_from` for choices; group by block id, call `carryOverDefault`, `UPDATE custom_forms_blocks_select SET default_value = ? WHERE id = ?` for each carried value, then print the report and write it to `forms-0.5.0-carry-over.txt` (form, section, question, locale, old value, reason per line). Then the backfill:

```sql
-- data only, no column default; same on each _v twin (version_ prefix on the forms table's columns):
UPDATE custom_forms_blocks_date SET mode = 'dayOnly' WHERE mode IS NULL;
UPDATE custom_forms_blocks_date SET value_format = 'local' WHERE value_format IS NULL;
UPDATE custom_forms_blocks_date SET display_style = 'asStored' WHERE display_style IS NULL;
UPDATE custom_forms SET send_another = 0 WHERE send_another IS NULL;            -- false on Postgres
UPDATE custom_forms_locales SET wording_send_another = 'Send another' WHERE wording_send_another IS NULL;  -- the site's words.sendAnother, per locale
```

drizzle-kit would generate a `DROP COLUMN` on the `_locales` tables and, for apps without localization, nothing for the defaults; neither is needed.

`down()`, in this order: (1) for each of the five block tables and each `_v` twin, read `id`, `default_value` (and `min_date`, `max_date` for date), call `rollbackDefault` (decision 18), write its `value` into the default-locale `_locales.default_value` row (`UPDATE … WHERE _parent_id = ? AND _locale = '<default locale>'`; insert the row with `_parent_id`, `_locale`, `default_value` when the update touched none), and write its `minDate`/`maxDate` back to the date block row, so `today` limits (and any time or date-time value) become `NULL`; print the report and write it to `forms-0.5.0-rollback.txt`; (2) `ALTER TABLE … DROP COLUMN` for each added column (none is indexed or a key; D1 supports it, and the QA rehearsal of 0.4.0 showed up/down/up works). Without localization, `default_value` was not added and is not dropped: step (1) writes `rollbackDefault`'s values back into the block table's own `default_value` and limits instead.

**Postgres:** the generated migration adds the columns and the new enum types and drops `default_value` from the `_locales` tables in the same file. Edit it so the copy, the report file and the backfill above run after the `ADD COLUMN` statements and before those drops, or delete the drops to keep the rollback simple (otherwise `down()` re-adds `_locales.default_value` before its step (1)); then `payload migrate`.

**Import map:** run `payload generate:importmap` after upgrading (new client components); without it the forms admin shows missing-component errors.

**Rollback:** run the migration's `down()` (`payload migrate:down`) on 0.5.0, then re-pin 0.4.0 and regenerate the import map. The `down()` is required, not optional: every form saved under 0.5.0 has lost its old `_locales.default_value` (Values that move), and a `today` limit left in place makes 0.4.0 refuse every date. With it, 0.4.0 reads the defaults as they stood under 0.5.0 (edits included) in the default language; other languages' old defaults survive only on forms never saved under 0.5.0, and values 0.4.0 can't read (a `today` default or limit, a time, a date-time) are dropped and listed in `forms-0.5.0-rollback.txt`. Answers stored as UTC instants stay as stored.

## Risks / Trade-offs

- **Data copy and backfill are part of the migration.** A site that runs only the `ADD COLUMN`s loses its email/number/date/select/radio defaults on screen and, on the starter, can't publish old forms (required wording). Mitigated: README and this section say so; the planner rehearses the hand-written migration on a 0.4.0 SQLite copy of the dev app before the publish, and the pin plan rehearses it on a QA D1 copy.
- **Async save hook** reads source collections for collection-choice defaults: one `find` per such question with a default, by ids; no read when the default is empty.
- **Rollback is a migration step, not a re-pin.** Payload rewrites block `_locales` rows on every save, so 0.4.0's old default column empties as forms are edited; only `down()` puts the defaults back (default language only), and it drops relative and time values 0.4.0 can't read. The report files are the record. Rehearsed by the planner (Workflow follow-up).
- **Time zone trust.** `_tz` comes from the visitor and is checked against `Intl` only, not against the visitor's real location. A false zone gives a wrong instant for a UTC-stored date-time, and can shift a `today` limit by a day for that visitor (a zone a day behind lets a "not before today" question accept yesterday's date; one a day ahead refuses today's); it only ever affects that visitor's own submission. The plugin's `timezone` applies when no zone is sent. Sites that don't want the zone stored set `metadata.timeZone: false` (decision 9); it is still used for that request.
- **Intl differences.** Display text depends on the runtime's ICU (Workers vs Node); tests compare with `Intl` output, not fixed strings.
- **Read-only submissions** stop admin scripts that patched answers; the plugin never did. Documented in the README note.
- **Parallel with job-055:** the security update (branch `update/2026-11-security`) touches `package.json`/`yarn.lock` and may merge to `main` while this builds. The builder doesn't fetch or rebase; the planner rebases after review (expected conflict `package.json`/`yarn.lock` only) and reruns the review on the rebased head. If it moves Payload past 3.92.1, the planner re-reads the Research lines for that version.
